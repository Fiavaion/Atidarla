## Engine design (pre-work)

- **Stable IDs:** `NodeId` is a per-network counter that is never reused. Node names (`noise1`) are unique and human-facing; IDs are what wires and files reference.
- **Deterministic order:** nodes and wires live in ordered maps and sets, so iteration and serialisation are stable (rule 8).
- **Typed wires:** an output connects only to an input of the same `WireType` (§5.4). PNT and MSH share `GEO`. An input holds at most one wire, and connecting replaces the old one. Cycles are rejected unless the input is declared as a feedback input (previous frame).
- **Edits and undo:** every change is an `Edit` that returns its inverse. A `Transaction` groups edits into one undo step and rolls back on error; the agent's accepted diffs use it later (FR-G2).
- **Pull cook:** consumers request outputs; the scheduler walks upstream and plans the nodes to cook in dependency order: dirty nodes, time-dependent nodes, and anything downstream of a node cooked this frame. Parameter and wiring edits mark the node and everything downstream dirty.
- **No allocation after warm-up:** the planner reuses its buffers, and a counting-allocator test enforces zero allocations in steady state (rule 2).
- **Metrics:** per-node cook time, as the latest value and an exponential moving average, always on (§5.3).

**Open design question for Mark (expressions, FR-P2):** rule 1 forbids blocking the render thread on Python, but the PRD puts a Python expression slot on every parameter. Proposal: (1) evaluate a small native expression subset (arithmetic, `time`, `me.digits`, channel/parameter references) in Rust on the cook path, which covers most real-world expressions; (2) run full Python expressions on the Python worker thread, with results latched for the next frame (one frame of latency) and shown as such in the UI. Needs a decision before expressions are built.
